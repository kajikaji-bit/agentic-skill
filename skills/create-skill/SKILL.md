# Create Skill

スキルは、成果物に至る手順と、手順が使う概念・役割・ルール・テンプレート・用語集・事例を一つのディレクトリに持つ。

## 規範の階層化と段階的一般化

行動を導く規範は、哲学や信念のように場面を越えて効くものから、個別の禁止や許可のように一つの場面にしか効かないものまで、抽象度の連続体に並ぶ。その連続体を段に切り、抽象度に合う語で呼び、隣り合う段だけを導出と検証で結ぶのが規範の階層である。上の段は下の段の理由を与え、下の段は上の段を確かめる材料になる。段を混ぜると、個別の取り決めを信念のように扱って過大評価したり、信念を一つの禁止に矮小化したりして、読み手が粒度を誤る。

上の段は最初から書けるものではない。人が個別の成果物へ返すフィードバックは、その人がまだ言葉にできていない暗黙知の現れであり、そこから直接に信念を書き起こすことはできない。実際に起きた事例から個別性を削ぎ落とし、一段ずつ上へ導くから、各段は一つ前の段で検証でき、暗黙知は事例に根を持ったまま形式知になり、その人がまだ言葉にしていない能力が使える形になる。段を飛ばして書いた信念やルールは、何に当てはまり何に当てはまらないかを確かめる元を持たない。スキルがすべての段を同じ場所に持つのは、次の段をどこから導いたかを辿り、下の段が変わったときに上の段を問い直せるようにするためである。スキルで作った成果物は次の事例になり、事例が増えるたびに上の段を問い直す。

## ドッグフーディング

Create Skill は Create Skill で改善する。このスキルもスキルの一つであり、これを使って作ったスキルと、それに依頼者が返したフィードバックは、そのままこのスキルの事例になる。段階的な一般化が働いているかは、その手順で自分自身を作り直せるかで確かめる。自分に当てはまらない手順は、他のスキルにも当てはまらない。自分に当ててみて初めて、手順の抜けや、段の切り方の粗さが、依頼者の指摘として現れる。

## 潜在能力を開拓する

- 相手の個別具体なフィードバックを、その人の背後に隠れた暗黙知の事例として扱い、その人の能力を引き出す
- 原則を、それを示す例と、他の場面にも当てはまる理由とともに書き残す
- 上位の階層を、一つ下の階層から導く
- ルールは領域の取り決めとして先に合意し、チェックは保証したいことの手段として作る
- 手順の中で使う語は、同梱した用語集の意味で使う

## ルール

- ルールは SKILL.md の「ルール」に書き、別ファイルへ分離しない
- 参照先は同じスキルの `references/` に閉じ、リポジトリの他の場所を参照しない
- 事例は実際にできた成果物とそれに返されたフィードバックから選び、架空の成果物を書かない
- 事例の原則には、それを示す例と一般原則で述べた理由を添え、成果物だけを写さない
- 各手順の終わりに、その手順で書いたものをチェック項目で確かめ、依頼者のレビューを受けてから次へ進む。満たさない項目と指摘はその手順の中で直す
- スキルのディレクトリ名には実行するプロセスを、テンプレートと事例のファイル名には成果物の名前を、用語集のファイル名にはその用語が使われるドメインを、チェックのファイル名には保証する内容を、レビューのファイル名には観点を書く

## 手順

1. 事例を集める
2. テンプレートと用語集を導く
3. ルールを定める
4. 概念と役割を書く
5. チェックとレビューを作る
6. 手順を書く

### 1. 事例を集める

スキルが作る成果物を一つ決め、その成果物を実際に作った場面と、そのとき残った成果物、それに返されたフィードバックを集める。新しいスキルなら名前を決め、このスキルと同じ skills ディレクトリに `<skill-name>/` を作り、`references/skill.template.md` を写して SKILL.md にする。既にあるスキルをブラッシュアップするなら、そのスキルで作った成果物とフィードバックを事例に加え、骨組みは作らない。以降は手順を一段ずつ進め、段ごとに一つ上がまだ成り立つかを依頼者と確かめる。成り立つと確かめられた手順で抜けてよい。

集めた事例から、再利用の見込みがある原則を取り出し、`references/example.template.md` に従い `references/<artifact>.example.md` に書く。原則ごとに、その原則を示す例と、他の場面にも適用できる一般原則で採用・不採用を説明する理由を書く。フィードバックで直された修正前は避ける例の、修正後は採用する例の候補になる。例は原則の理解に必要なものだけを選び、片方だけでもよい。比較する例は同じ目的・場面を扱う。事例に無いものを書き足さない。

### 2. テンプレートと用語集を導く

採用する例から個別性を削ぎ落とし、見出しと空欄と記入上の注意だけを `references/<artifact>.template.md` に残す。空欄は `{}` に埋める値の名前を、注意は `<!-- -->` に記入例と制約を書く。避ける例からは、構造として避ける形と、テンプレートを適用してよい条件を取り出し、記入上の注意に加える。採用する例を埋め直してテンプレートに戻ること、避ける例が注意に引っかかることを確かめる。

事例に書いた理由から、原則を述べるのに使った概念を取り出し、`references/<domain>.terminology.md` に `references/layers-of-guiding.terminology.md` の書式で語と意味を書く。本文に現れた語を拾うのではなく、理由を述べるのに要った概念を集める。意味は依頼者と確認し、以後の手順はその語で書く。

### 3. ルールを定める

テンプレートの見出し・空欄・注意から、この領域で先に合意しておく取り決めを発見し、用語集の語で SKILL.md の「ルール」に書く。用語集の語の意味から見えてくる視点も、取り決めを発見する手がかりにする。ルールは成果物の統一感を保ち、作るときの摩擦を減らすためのもので、守られているかを判定する手段は手順 5 で別に作る。ルールをテンプレートと採用する例に当てて満たすこと、避ける例に当てて破ることを確かめる。

### 4. 概念と役割を書く

ルールを抽象化し、なぜそうするかの主張を概念として SKILL.md の「概念」の節に、見出しと段落で書く。作り手が成果物を作るときに保つ姿勢を行動原理として取り出し、それを持つ役割に名前を付けて、行動原理を箇条書きにする。各ルールが概念か行動原理のいずれかから導けることを確かめる。

### 5. チェックとレビューを作る

成果物について保証したいことを決め、保証したいことごとに `references/checks/<guarantee>.md` を作り、ルールを基準に Yes／No で確かめられる項目を書く。ルールとチェックは一対一でなくてよく、一つの保証が複数のルールに依ることも、チェックを持たないルールがあることもある。

役割の行動原理を観点にして、観点ごとに `references/reviews/<standpoint>.md` を作り、成果物が望ましい状態にあるかを見てギャップを見出すための問いを書く。

### 6. 手順を書く

骨組みの SKILL.md の残りのプレースホルダに、手順と参考を記入する。手順は、手順 1 から 5 で揃えた参照先をどの段階で使うかを示す順に書く。テンプレートのコメントを消す。手順のどこからも参照されない参照先は消し、「参考」の一覧からも外す。
